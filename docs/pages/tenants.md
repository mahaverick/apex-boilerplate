# Tenants

The tenant list (`/tenants/`), a tenant's tabs under `/tenants/$tenantId`, and the tenant actions menu. Back to the [route map](README.md#route-map).

## Layout

`/tenants/$tenantId` (`src/pages/_app/tenants/$tenantId.tsx`) is the layout every tenant tab renders in, under `AppLayout` ([overview.md](overview.md#the-staff-shell)).

|                 |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fetches         | Its loader starts `GET /platform/tenants/:id` (`['platform', 'tenant', id]`; a 404 is not retried) without awaiting it, so the router never holds the page: the layout draws at once. On a first visit, when the route's code takes more than 300 ms to arrive, `DetailPending` shows until it does; there is no boot wait beyond `_app`'s flags read. Every tab reads the same cached detail.                                                                                                                                                                                                                                                                                                                                                  |
| While it loads  | A visually hidden `h1` "Tenant" over the header's shape: a name bar (`h-8 w-64`) and a line bar (`h-5 w-48`) beside an actions bar (`h-9 w-28`), then the real tab bar and the `Outlet`. Overview, Flags, Onboarding and Emails draw their own skeletons; Members, Invitations and Activity stay blank until the detail is in. The loaded header replaces only the skeleton part. The breadcrumb reads Tenants › Tenant › {tab} until the detail is in. The skeleton's sizes follow the loaded header's text sizes; they were not measured against it. While the tenant loads the layout's root is `aria-busy`.                                                                                                                                 |
| Gate panels     | A 404 renders an `EmptyState` with the `h1` **Tenant not found**, "It doesn’t exist, or your role changed. If your role changed, reload the page." and Back to tenants. Any other failure renders one `LoadError`, "We couldn’t load this tenant. Select Try again.", whose Try again refetches the detail; it replaces the header, the tabs and the tab, and offers no way back but the breadcrumb. A failed refetch while the tenant is on screen keeps the header, the tabs and the tab, with the same `LoadError` above them; only a 404 still replaces the page.                                                                                                                                                                           |
| Header and tabs | The tenant's name as the `h1` with its state badge (`TenantStateBadge`), then "`{slug}` · Created {date}", and the **Actions** menu on the right. Below, a `nav` "Tenant sections" of link tabs (bottom-bordered `Link`s, hand-rolled): Overview, Members, Invitations, Activity, Emails, Onboarding, Billing, Flags. Flags has `minRole: 'admin'` in `TENANT_DETAIL_TABS` (`src/constants/tenant-tabs.ts`) and is left out of the nav below admin. Billing has `customerOnly`, so the platform tenant (the staff team), which has no billing, leaves it out. On a phone the bar scrolls sideways with no sign that more tabs follow.                                                                                                           |
| Actions menu    | `TenantActionsMenu` (`src/components/features/tenants/tenant-actions-menu.tsx`), shown only when one action applies: Edit details, Resend owner invitation (no active owner), Suspend, Reactivate, Archive (admins and up, by lifecycle state) and Delete permanently (owners, archived tenants). Each opens a dialog; the destructive ones go through `ReasonDialog` and the shared step-up dialog. Suspend, Archive and Delete permanently each add one sentence on billing: with payments on, Paid is cancelled at the end of its paid period (or now if it hasn't been charged yet), or cancelled now (express queues no cancel with payments off); or it must be cancelled before express allows the delete. A viewer gets no menu at all. |
| Breadcrumbs     | Tenants › {name} › {tab}. The name comes from the same detail query (`TenantCrumb`), so it reads "Tenant" while the detail loads.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |

In the walk, a load of `/tenants/{id}/members` with the detail held for 2.5 s showed the shell, the breadcrumb Tenants › Tenant › Members and the header skeleton for the whole 2.5 s; the members request started only after the detail answered. With only `GET /tenants/:slug/members` failing, the header and tabs stayed and the Members card showed its own `LoadError`. The capture's error shots fail the detail, so every tab's error shot is the layout's `LoadError` alone.

### `/tenants/$tenantId/invitations` — Invitations

![Invitations](img/tenants/tenant-invitations--default.jpg)

|                     |                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Purpose             | Invite someone to the tenant, and resend or revoke pending invitations.                                                                                                                                                                                                                                                                                                                               |
| File                | `src/pages/_app/tenants/$tenantId.invitations.tsx`                                                                                                                                                                                                                                                                                                                                                    |
| Guard and redirects | `_app`, then the [layout](#layout); `FrozenTenant` for a non-active tenant. Below the tenant's owner or admin role the tab says "Invitations are managed by owners and admins. Your role here can’t see them." and asks for no list.                                                                                                                                                                  |
| Layout              | `AppLayout` › tenant layout                                                                                                                                                                                                                                                                                                                                                                           |
| Data                | after the layout's detail: `GET /tenants/:slug` (the role), then `GET /tenants/:slug/invitations?search&role&sort&cursor&direction&limit&total=1` (`['tenants', slug, 'invitations', { tenantId }, request]`) once the role allows it; `POST` invite, resend and revoke. Its URL keys are prefixed (`invitationsSearch`, `invitationsSort`, `invitationsRole`) so the members list can share a route. |
| Sections            | **Invite a member** card (`InviteMemberForm`: email, role `Select`, Invite member). **Pending invitations** card (`PendingInvitations`): a `DataTable` of Email, Role, Invited (date and inviter), Expires and Actions (Resend and Revoke), with a search box, a Role facet and cursor paging; below `md` one bordered card per invitation.                                                           |
| Components          | `Card`, `Form`, `Input`, `Select`, `Button`, `LoadError`, `ReasonDialog`, `AlertDialog`; `EmptyState` (compact); `DataTable` through `PendingInvitations` (`Item` on phones)                                                                                                                                                                                                                          |
| Transitions         | none beyond the tabs                                                                                                                                                                                                                                                                                                                                                                                  |

An invite into a tenant at its members limit gets a 402 `PLAN_LIMIT_REACHED` whose sentence tells the customer to upgrade. The form words it for staff instead, at form level: "Not sent. {tenant} has {used} of {limit} members on {plan}. Add a Members grant on its Billing tab to invite more.", ("member" after a limit of 1), with an "Open Billing" link that takes focus, on the staff path and the member path alike. The platform tenant has no Billing tab, so its refusal shows the API's sentence and no link. Staff below platform manager read "Ask a platform manager to add a Members grant on its Billing tab." instead. The plan's name comes only from cached data: a billing view the Billing tab cached, or the tenant's row in a cached Tenants list with the name from `GET /platform/plans`. The form never reads the tenant's billing, which express records as a `billing.viewed` audit entry; with no cached plan the sentence leaves "on {plan}" out.

Resend is disabled while the invitation's resend cooldown runs, reading "Resend in 4 min" or "Resend in 42 seconds" from the row's `resendAvailableAt` or a 429's `Retry-After`, and stays focusable; it opens again on its own, with no refetch. The capture's tenant has no pending invitation, so the default and empty shots are the same page.

The Billing card's **Actions** menu (labelled "Billing actions", `BillingActionsMenu`) and each active grant's **Revoke** button are the tab's writes. Each shows only for a role and state express accepts (`billingActionsFor` in `src/lib/billing-actions.ts`), and a viewer gets none, not even the grants table's actions column. Every write goes through step-up and carries a reason; refusals show the API's sentence in the dialog. Express masks every 5xx body, so two outages are worded here from the code and `Retry-After`: a busy billing row (503 `BILLING_BUSY`) reads "Billing for {tenant} is updating. Try again in {n} seconds.", a provider with no answer (503 `PAYMENT_PROVIDER_UNAVAILABLE`) "Razorpay didn't answer. Try again in {n} seconds. If it keeps failing, check Razorpay's status page.", and a refused request (502) "Razorpay didn't accept this request. Check {tenant} in Razorpay's dashboard." With no `Retry-After` the wait reads "a minute". The palette lists the menu's items under This page.

Every date on the tab and in its toasts reads in the tenant's time zone (`settings.timezone` from its detail; UTC until the detail is read), month spelled out ("20 November 2026"), as react's billing page and express's billing emails write it, so staff and the customer name the same day; a date and time also names the zone ("20 November 2026 at 05:30 GMT+5:30"). The Plans page's price dates and the Billing alerts list belong to no one tenant, so they read in your own zone. The summary's rows follow react's billing page: "Trial ends" only while the tenant is trialing (express keeps the trial date afterwards; a trial that ends while the page is open reads as Free, as express's effective state serves it, and so does a failed payment past its grace), "First charge {price} on {date}" for a tenant that took Paid during its trial and has not been charged, "Next subscription" ("₹9,990 per year from {date}", or "Yearly from {date}" without the plans) for an active tenant with a next subscription booked, checked first as react does, "Cancels on" in place of "Paid until" while the subscription ends at its period end, and "Period ended" with "Moves to Free on" (three days later, express's buffer) once a cancelled period has ended; past that day the tenant reads as Free and shows no dates, as express serves it and as the cancel dialog reads it. Free shows no dates, since express keeps the last period's end after the move. It also shows "Payment failed on {date}. Paid ends on {date}." or "… Razorpay is still retrying the payment." (and "Razorpay paused the subscription." when paused) for a failed payment, "Dispute open" as a destructive badge, and copy buttons for each subscription id. With payments off, a note says "Payments are off on this server. This page shows the stored plan and dates. Nobody can be charged, and Resync and Cancel are hidden.", the subscription ids are left out, and the Invoices card says they can't be read and asks nothing. The billing email is owner-only, so staff never see it. Payer names, grant authors and grant reasons are masked (`Pii`).

Usage and access lists each catalog entry: a limit as "{used} of {limit} {label}" or "{used} {label} · No limit", the label lower-cased and singular after a count of 1 ("1 of 1 member", "4 of 50 members"), counts grouped as "1,000,000", with Near limit or At limit, a feature as On or Off, and a Plan or Grant badge. Without the plans each row shows its registry key.

State history's search box reads "Search by state or cause, such as Payment failed" and sends a whole state or cause label ("Payment failed", any case) as its stored code (`past_due`), since express matches stored codes; any other term goes as typed. Provider events read "Not yet" in Handled while pending and "Gave up" once failed; only a failed event's error is red, and an unused event's reason is muted.

The Invoices card ("Razorpay lists invoices newest first and offers no search or sort."; an issued invoice reads "Not paid", as react words it) reads the provider forward only, newest subscription first, 20 invoices a page at most. It has a Status filter, kept in the card for simplicity, and no search or sort, which the provider does not offer. Its query does not refetch on window focus, since each loaded page is a provider read. A page can come back short or empty while more remain, so "Load more invoices" stays while the provider says there is more, and "No invoices for this tenant." shows only once it says there is none. A refused cursor (the subscriptions changed, or payments were turned off) offers "Start again from the newest", which also reads the billing again, so payments turned off show as the payments-off note. A failure shows the API's sentence with Try again; a failed Load more keeps the invoices already read. Invoices carry no link: the provider's page shows the payer's contact details.
